# Paper Trading Agent

Агент, торгующий в реальном времени **виртуальными деньгами** — реальных
ордеров на бирже не размещает и не может разместить (в коде физически нет
вызовов к authenticated-эндпоинтам бирж, только публичное чтение котировок).
Решения принимает исключительно на основе данных, которые сам успел
пронаблюдать в потоке — без подглядывания в будущее.

Два готовых сценария:
- `run_agent.py` — базовый агент на любом символе, сигнал по SMA-пересечению цены.
- `run_eth_news_agent.py` — **фокус на ETH**: решение строится только на
  новостном потоке по Ethereum через последовательное байесовское обновление
  вероятности (см. раздел [«ETH news-агент»](#eth-news-агент-run_eth_news_agentpy) ниже).

## Гарантии (что агент НЕ делает)

- Не использует и не запрашивает API-ключи биржи.
- Не импортирует и не вызывает ничего, что размещает реальный ордер.
- Не торгует с плечом, не открывает шорты (упрощение для paper-режима).
- Стратегия получает только `price_history` — буфер, который сам агент
  накопил по ходу опроса; это гарантирует отсутствие lookahead-bias,
  типичного для бэктестов "задним числом".

## Быстрый старт (без доступа в интернет — симулированный фид)

```bash
cd paper_trading_agent
pip install -r requirements.txt
python run_agent.py --data-source simulated --symbol DEMOUSDT \
    --interval 1 --max-iterations 200
```

Лог каждой итерации пишется в `state/trade_log.csv`, текущее состояние
портфеля — в `state/portfolio.json` (обновляется на каждом шаге, можно
смотреть параллельно с работающим агентом).

## Live-режим (реальные котировки биржи, всё ещё виртуальные деньги)

```bash
python run_agent.py --data-source live --symbol BTCUSDT --interval 15
```

Источник `live` — публичный REST-эндпоинт Binance `ticker/price` (без
авторизации). Работает на машине с доступом в интернет к `api.binance.com`;
в этой песочнице сетевая политика блокирует исходящие запросы к биржам —
поэтому для проверки в текущем окружении используется `--data-source
simulated`, а `live` нужно проверять там, где сеть разрешена (локально,
на VPS и т.п.).

Для непрерывной работы (24/7) запускайте через `systemd`, `screen`/`tmux`,
`nohup` или как контейнер — без `--max-iterations` цикл идёт бесконечно,
пока не будет остановлен (Ctrl+C или сигнал процессу).

## ETH news-агент (`run_eth_news_agent.py`)

Решение строится ТОЛЬКО на новостном потоке по ETH, через ту же
теоретико-вероятностную машинерию, что в `news_strategy/`:

1. **Офлайн-обучение перед стартом.** `src/eth_training_data.py` генерирует
   историю ETH-новостей (в реальном использовании — заменяется на
   исторические данные CryptoPanic + цены ETH), прогоняет `event_study_by_type`
   и печатает, какие типы новостей вообще статистически значимо двигают цену
   (в демо-прогоне значим только `hack`, p≈0.004 — остальные в пределах шума
   при таком объёме истории). Затем `BayesianNewsModel.fit` оценивает
   правдоподобия `P(тип+сентимент | рост)` на этой истории.
2. **Live-цикл.** `NewsAwareStrategy` (`src/strategy.py`) держит `belief_up` —
   текущее байесовское убеждение о вероятности роста. На каждую новую
   новость применяется правило Байеса (апостериорная вероятность предыдущего
   шага становится априорной для следующей новости — последовательное
   обновление). Между новостями `belief_up` экспоненциально затухает к
   базовому prior модели (`--decay-half-life-sec`, по умолчанию час) —
   влияние новости на рынок не вечно.
3. Вход в лонг при `belief_up >= --entry-threshold` (по умолчанию 0.58),
   выход при `belief_up <= --exit-threshold` (0.50) или по стоп-лоссу/тейк-профиту.

```bash
# Демо на симулированных цене + новостях (для этой песочницы)
python run_eth_news_agent.py --data-source simulated --news-source simulated \
    --interval 1 --max-iterations 300

# Live: реальные котировки Binance + реальная лента CryptoPanic по ETH
# (нужен доступ в интернет; CRYPTOPANIC_TOKEN -- бесплатный, read-only,
# не привязан к биржевому аккаунту)
CRYPTOPANIC_TOKEN=... python run_eth_news_agent.py \
    --data-source live --news-source live --interval 30
```

Лог новостей и итоговое `belief_up` после каждой сохраняются в
`state_eth/news_log.csv` — можно проследить, какая именно новость и почему
сдвинула решение агента.

## Архитектура

```
run_agent.py               # CLI для базового SMA-агента на произвольном символе
run_eth_news_agent.py       # CLI для ETH news-агента: офлайн-обучение -> live-цикл
src/
├── market_data.py           # источники цены: BinancePublicDataSource (live) / SimulatedDataSource
├── news_source.py            # источники новостей: CryptoPanicNewsSource (live) / SimulatedEthNewsSource
├── news_text_gen.py           # генерация текста синтетических ETH-новостей по категориям
├── sentiment.py                 # лексиконный сентимент-скорер (копия из news_strategy/)
├── bayesian.py                   # BayesianNewsModel -- байесовское обновление (копия из news_strategy/)
├── event_study.py                 # CAR + t-тест значимости типа новости (копия из news_strategy/)
├── eth_training_data.py            # офлайн: синтетическая история ETH -> event study -> fit модели
├── portfolio.py                     # PaperPortfolio -- виртуальные cash/позиция/сделки, JSON-снапшот
├── strategy.py                       # SmaCrossoverStrategy и NewsAwareStrategy
├── risk.py                            # RiskManager -- сайзинг, стоп-лосс/тейк-профит, дневной лимит убытков
└── agent.py                            # TradingAgent -- главный цикл: цена+новости -> сигнал -> риск -> сделка -> лог
```

## Параметры риск-менеджмента (см. также `crypto-trading-guide.md` в корне репозитория)

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--risk-per-trade-pct` | 0.02 | базовая доля кэша на вход, масштабируется уверенностью сигнала |
| `--stop-loss-pct` | 0.03 | закрыть позицию при просадке от цены входа |
| `--take-profit-pct` | 0.06 | закрыть позицию при прибыли от цены входа |
| `--daily-loss-limit-pct` | 0.05 | остановить открытие новых позиций при дневной просадке капитала |

Приоритет в цикле агента: **стоп-лосс/тейк-профит уже открытой позиции
всегда проверяются раньше нового сигнала стратегии** — так агент не
проигнорирует управление риском ради нового входа.

## Проверено в этой сессии

- **`run_agent.py`**: 80 итераций на `SimulatedDataSource` (низкая
  волатильность) — 1 полный цикл buy → sell по сигналу SMA; 300 итераций
  при повышенной волатильности — сработали все три ветки выхода
  (`stop_loss`, `take_profit`, `signal_flat`).
- **`run_eth_news_agent.py`**: офлайн-обучение корректно выделяет значимый
  тип новости (`hack`, p≈0.004) на синтетической истории. Live-цикл с
  ускоренным потоком новостей (для проверки в разумное время) отработал
  весь путь: новость → сентимент+тип → байесовское обновление `belief_up`
  → вход в лонг при пересечении порога → выход как по сигналу, так и по
  стоп-лоссу. На реалистичной интенсивности новостей (по умолчанию
  3/час) агент корректно проводит большую часть времени без новых
  новостей, ожидаемо — как и было бы в реальности.

## Ограничения и что нужно доработать перед реальным использованием капитала

- **SMA-стратегия (`run_agent.py`) — учебный пример.** Пересечение скользящих
  средних на одном активе без учёта новостей/режима рынка не является
  готовой прибыльной стратегией сама по себе.
- **ETH news-агент решает только по новостям**, полностью игнорируя ценовое
  движение как источник сигнала (по требованию задачи) — на практике для
  реальных денег обычно комбинируют новостной сигнал с ценовым/объёмным
  фильтром (см. `news_strategy/README.md`: событийный анализ + режимы рынка
  через HMM). Риск переобучения, устаревания сигнала и поправка на multiple
  testing — все предостережения из `news_strategy/README.md` применимы и
  здесь, в том числе разреженность признака `event_type + sentiment_bucket`
  при малом объёме исторических новостей.
- **CryptoPanic-эвристика категорий грубая** (`_infer_event_type` в
  `news_source.py` — поиск ключевых слов в заголовке). Для реального
  использования замените на нормальную классификацию (NLP-модель или
  структурированные категории самого API/другого поставщика новостей).
- **REST-поллинг, не WebSocket.** Для по-настоящему низкой задержки на
  реальном live-режиме лучше подключить WebSocket-стрим биржи вместо
  периодического REST-опроса — сейчас это самый простой вариант, работает
  надёжно, но не минимизирует задержку.
- **Один актив, без диверсификации.** Текущая версия ведёт позицию по
  одному символу; расширение на портфель из нескольких активов потребует
  отдельного риск-бюджета на актив (см. диверсификацию в
  `crypto-trading-guide.md`).
- Это остаётся симуляцией: реальное проскальзывание, частичное исполнение
  и реальная книга заявок не смоделированы (комиссия учтена как фиксированный
  процент). Прежде чем переходить к реальным деньгам, нужен более
  реалистичный backtesting/forward-testing период и отдельное решение о
  переходе на реальное исполнение — это не входит в scope этого агента.
